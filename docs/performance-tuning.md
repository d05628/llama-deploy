# 性能调优日志：Qwen3.8-27B on RTX 5060 Ti 16GB

记录一次完整的吐字速度优化过程：**6.39 → 26.3 token/s（4.1×，输出保真度不变）**，
极速档可达 34–56 t/s（5.3–8.8×，但输出会与参考解码不同）。

包含有效手段、**无效手段**、量化档位的质量实测、推测解码的无损性验证，以及复现方法。
无效路径同样记录在案，避免重复踩坑。

---

## 1. 环境

| 项 | 值 |
|---|---|
| GPU | RTX 5060 Ti 16GB（Blackwell, compute capability 12.0），显存带宽规格 448 GB/s |
| CPU | AMD Ryzen 5 5600（6 核 12 线程） |
| 内存 | 64 GB DDR4-2133（实测有效带宽约 17 GB/s） |
| 模型 | `Qwen3.8-27B-UD-Q4_K_M.gguf`，27.32B 参数，4.82 BPW，**15.32 GiB** |
| 架构 | `qwen35` —— 混合注意力：64 层中每 4 层才有 1 层全注意力，其余为常数大小的 SSM 循环状态 |
| llama.cpp | build 10783 (f45576aa8) |

## 2. 根因：不是参数没调好，是显存装不下

```
权重                        15.32 GiB
可用显存（16.0 - 桌面占用）   ≈14.6 GiB
```

权重本身就超出可用显存。原配置 `ctx_size: 65536` 还要再吃 **2176 MiB** KV cache，
于是 llama.cpp 的 `--fit` 只能把大量层留在 CPU 上。这些层跑在 DDR4-2133 上
（约 17 GB/s，是显存的 1/20），成为绝对瓶颈。

**这个过程 llama.cpp 全程没有任何提示** —— 服务照常启动，只是慢了 3 倍。

### 对照实验：硬件本身没问题

同一张卡跑能完整驻留显存的 `gemma-4-12b-it-Q4_K_M`（6.63 GiB）：

```
48.88 token/s  →  有效带宽 348 GB/s  =  规格 448 GB/s 的 78%
```

这是健康的利用率。问题 100% 在显存容量，不在算力或驱动。

## 3. 有效优化

全部为端到端实测（`llama-server` + HTTP 请求，每项 3 次取中位数，n_predict=160）。

### 3.1 上下文长度 —— 决定性因素

KV cache 每多占 1 GiB，就有约 4 层权重被挤到 CPU。

| ctx_size | KV cache (q8_0) | 吐字速度 |
|---:|---:|---:|
| 65536 | 2176 MiB | 6.39 t/s |
| 32768 | 1088 MiB | 9.14 t/s |
| 16384 | 544 MiB | 12.60 t/s |
| 8192 | 272 MiB | 15.78 t/s |

### 3.2 KV cache 量化

`q4_0` 把 16k 上下文的 KV 从 544 MiB 压到 288 MiB，省下的显存换成权重驻留：

| ctx | KV 类型 | 吐字速度 |
|---:|---|---:|
| 16384 | q8_0 / q8_0 | 12.60 t/s |
| 16384 | q8_0 / q4_0 | 13.07 t/s |
| 16384 | **q4_0 / q4_0** | **15.30 t/s** |

**等价交换**：`ctx 16384 + q4_0` ≈ `ctx 8192 + q8_0`（都约 16 t/s）。
在"上下文长度"和"KV 精度"之间二选一，速度相同。

### 3.3 batch / ubatch

小 ubatch 意味着更小的计算缓冲，能多塞下权重。但过小会拖慢提示词处理：

| -b / -ub | 吐字 | 长提示词处理 |
|---|---:|---:|
| 1024 / 128 | 16.38 t/s | 621 t/s |
| **1024 / 256** | **16.38 t/s** | **~435 t/s** |
| 2048 / 512 | 15.86 t/s | 411 t/s |

`ub 256` 是拐点。

### 3.4 `--fit-target`（显存余量）

权重比显存大时，留给驱动的余量每多一点，就少一点权重驻留 GPU：

| fit-target | 吐字速度 | 实测显存占用 |
|---:|---:|---:|
| 256 MiB | 14.62 t/s | 15630 MB |
| **64 MiB** | **16.77 t/s** | 15804 MB |

代价是显存余量更紧。若运行期间会开游戏或大量浏览器标签，改回 `256` 更稳。

### 3.5 最终配置

```jsonc
"server":      { "ctx_size": 16384 }
"performance": { "batch_size": 1024, "ubatch_size": 256,
                 "cache_type_k": "q4_0", "cache_type_v": "q4_0" }
```

端到端实测：**16.34 t/s（散文）/ 16.12 t/s（代码）**，长提示词处理 435 t/s。

## 4. 无效路径（已验证，不要重复尝试）

### 4.1 `-ot token_embd.weight=CPU` —— 严重倒退

思路看似成立：`token_embd.weight` 有 **682 MiB**（词表 248320 很大），
而它每 token 只做一次行查表，放 CPU 几乎零算力成本。而 ctx 16k 下正好差 689 MiB。

**结果：12.91 → 8.41 t/s。**

原因：`-ot` 会干扰 `--fit` 自带的**张量级**自动放置。`--fit` 本身就在做
"filling dense layers back-to-front"（可从 `-v` 日志确认），手工 `-ot` 反而把它
挤回更笨的整层策略。三种上下文长度下速度都锁在 8.2–8.4 t/s，说明自动放置已被禁用。

> 教训：`--fit on` 已经很聪明，不要用 `-ot` 去"帮"它。

### 4.2 `--spec-type draft-mtp` —— 显存换不来速度

模型确实带 MTP 头（`blk.64.nextn.*`），llama.cpp 也支持 `draft-mtp`。

**结果：15.98 → 11.90 t/s（代码），15.78 → 8.71 t/s（散文）。**

原因：MTP 层要多占约 350 MiB 显存（实测显存占用从 15791 降到 15431，即多出的
权重被挤到 CPU）。在显存本就不够的机器上，推测解码省下的前向次数，远补不回
被挤到 CPU 上的那几层的代价。

> 结论：**显存吃紧时不要开推测解码。** 等权重能完整驻留显存再考虑。

### 4.3 `--spec-type ngram-*` —— 噪声级别

`ngram-map-k` / `ngram-mod` 不需要草稿模型、不占显存，理论上很有吸引力。

**结果：+2% ~ +6%，在测量噪声内。**

⚠️ 过程中有一次测到 21.27 t/s（相对基线 +45%），**中位数复测后没能复现**，
是异常值。这也是本次调优全部改用"3 次取中位数"的原因 —— 单次测量在这台机器上
波动可达 ±30%，足以得出完全错误的结论。

> 教训：任何单次跑出的"大幅提升"都要复测。

### 4.4 其它

| 手段 | 结果 |
|---|---|
| `-ngl` 手工指定（52/56/58） | 均劣于 `-ngl auto --fit on`，因为手工整层卸载会把对应层的 KV 也留在 CPU |
| `-ub 128` | 吐字无增益，长提示词处理反而下降 |
| `-t 5`（避让 CUDA 驱动线程） | 14.77 vs 14.55，无显著差异 |
| `--cache-reuse 512` | 混合/循环架构不支持，llama.cpp 启动时自动禁用（无害，但日志会有一条误导性警告） |

## 5. 复现方法

```bash
# 查看当前配置实际生成的启动参数与显存诊断
python -c "import run; rt=run.runtime(run.parse_jsonc(run.CONFIG_FILE),'server'); \
           print(' '.join(map(str,rt['args']))); [print('•',w) for w in rt['warn']]"

# 官方基准（pp = 提示词处理，tg = 吐字）
python run.py --benchmark
```

测量吐字速度时注意：

1. **必须重复测量取中位数**，单次结果不可信（见 4.3）。
2. 先发一次短请求预热，再测。
3. 关注 `nvidia-smi` 的显存占用：接近 16000 MB 说明显存已用满，
   此时任何"省显存"的改动都会直接转化为速度。

## 6. 还能再快吗

到这一步，剩余瓶颈仍然是"权重装不下"。两条路：

1. **换更小的量化档位**，让权重完整驻留显存 —— 见第 7 节，有实测数据。
2. **腾显存**。桌面 + 浏览器占用约 1.4 GiB；关掉浏览器硬件加速可省 0.7–1 GiB，
   直接换成更多层驻留 GPU。（Ryzen 5 5600 无核显，显示输出只能走这张卡。）

## 7. 量化档位选择（实测）

### 7.1 现用文件其实不是普通 Q4_K_M

`UD-Q4_K_M` 是 Unsloth 的**动态混合量化**，逐张量分配精度：

| 类型 | 张量数 | 占用 | 占比 | 实际 bpw |
|---|---:|---:|---:|---:|
| Q5_K | 131 | 4.50 GiB | 29.4% | 5.50 |
| IQ4_XS | 117 | 4.43 GiB | 28.9% | 4.25 |
| Q4_K | 104 | 3.92 GiB | 25.5% | 4.50 |
| Q6_K | 30 | 1.69 GiB | 11.0% | 6.56 |
| 其它 | 483 | 0.79 GiB | 5.1% | — |

**它已经在用 IQ4_XS**（占 29%），同时把关键张量保护在 Q5_K / Q6_K。
所以"IQ4_XS 会大幅掉智商"这个担心，对 UD 系列并不成立 ——
换 `UD-IQ4_XS` 只是把这个保护策略放到更小的预算里执行，不是换成劣质格式。

### 7.2 质量实测

用同架构的 `Qwen3.5-2B-BF16`（`qwen35`，同样 `full_attention_interval=4`）做代理，
统一 imatrix（校准集 `manager.py` + `deploy.py`），**留出**评测集
（`README.md` + `compat.py` + `run.py`，与校准集无重叠）：

| 档位 | 困惑度 | vs BF16 | 体积 | 吐字速度 |
|---|---:|---:|---:|---:|
| BF16 | 3.5545 | — | 3.52 GiB | — |
| Q4_K_M | 3.6429 | **+2.49%** | 1.19 GiB | 233.2 t/s |
| Q4_K_S | 3.6574 | +2.89% | 1.13 GiB | 245.7 t/s |
| **IQ4_XS** | 3.6639 | **+3.08%** | 1.11 GiB | **234.9 t/s** |
| Q3_K_M | 3.8996 | **+9.71%** | 1.02 GiB | 226.4 t/s |

三条结论：

1. **IQ4_XS 与 Q4_K_M 的质量差距只有 0.6 个百分点。**
2. **Q3 是真的掉**：+9.71%，约为 Q4 档的 4 倍。避开 Q3 的直觉是对的。
3. **Blackwell 上 i-quant 没有速度惩罚**：IQ4_XS 234.9 vs Q4_K_M 233.2 t/s，
   基本持平。"i-quant 在 CUDA 上慢"的说法在这张卡上不成立。

> ⚠️ 2B 代理会**高估**量化损失 —— 参数越少对量化越敏感。27B 的真实差距应小于上表。

### 7.3 关于"针对 50 系优化的量化格式"

**不存在。** llama.cpp 的 CUDA 后端对所有 K-quant / i-quant 都是先反量化成 FP16
再走标准 tensor core，量化格式本身与 GPU 架构无关。

- Blackwell 原生的 FP4/FP8 加速要靠 TensorRT-LLM / vLLM 的 NVFP4 路径，
  llama.cpp 用不上，而且那条路需要更多显存，Windows 上部署也很麻烦。
- `MXFP4` llama.cpp 确实支持，但它是给原生以 MXFP4 发布的模型用的；
  把普通模型重量化成 MXFP4，同体积下质量不如 IQ4_XS。
- 唯一有实质的架构顾虑是"i-quant 在新卡上慢不慢"，7.2 已实测否定。

### 7.4 建议

按 [unsloth/Qwen3.8-27B-GGUF](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF) 的实际体积：

| 档位 | 体积 | 权重能否完整驻留 16GB |
|---|---:|---|
| UD-Q4_K_XL | 16.35 GiB | ❌ |
| UD-Q4_K_M（现用） | 15.33 GiB | ❌ 溢出约 1.9 GiB |
| UD-Q4_K_S | 14.30 GiB | ❌ 仍溢出约 0.9 GiB |
| **UD-IQ4_XS** | **13.28 GiB** | ✅ |
| UD-Q3_K_XL | 12.24 GiB | ✅ 但质量代价大（见 7.2） |

显存预算：可用 14.57 GiB − 运行开销约 0.59 GiB − KV(16k, q8_0) 0.53 GiB
= **13.45 GiB** 可供权重使用。

**`UD-IQ4_XS`（13.28 GiB）是唯一既装得下、质量又几乎不降的档位。**
换过去以后还能把 KV cache 改回精度更高的 `q8_0`：

```jsonc
"model":       { "model_file": "Qwen3.8-27B-UD-IQ4_XS.gguf" }
"server":      { "ctx_size": 16384 }
"performance": { "cache_type_k": "q8_0", "cache_type_v": "q8_0" }
```

也可选 `ctx_size: 32768` + `q4_0` KV，同样装得下。

### 7.5 换档后的实测结果

已实机验证（`ctx 16384`、`q4_0` KV、`ub 256`、`fit-target 64`，3 次取中位数）：

| 阶段 | 吐字速度 | 提示词处理 |
|---|---:|---:|
| 起点：Q4_K_M + ctx 65536 | 6.39 t/s | 28 t/s |
| 调参后：Q4_K_M + ctx 16384 | 16.34 t/s | 435 t/s |
| **换档后：UD-IQ4_XS** | **25.4 t/s** | **603 t/s** |

**相对起点提升 4.0 倍**，且比外推的 20–24 t/s 还略高。
显存占用 14493MiB，权重完整驻留。

## 8. 视觉模式的显存代价

同一个模型、同一份配置，**以视觉模式启动只有 4–5 t/s**，是文本模式的六分之一。

原因是视觉模式有两笔额外开销：

| 项目 | 占用 |
|---|---:|
| `mmproj-bf16.gguf` 常驻显存 | 888 MiB |
| `fit_target` 由 64 抬到 `mmproj×1.1+512` | 1488 MiB |
| 合计 | **约 2376 MiB** |

13.27GB 的权重本来刚好装得下，这 2.3GB 一挤，约 **1537MiB 权重被迫回到 CPU**，
于是又回到"部分层跑在 DDR4 上"的慢速状态。

**这笔开销此前完全没有提示**（v1.2.0 的显存诊断没把视觉模式算进预算）。
自 v1.3.1 起，视觉模式下启动会明确告知：

> 视觉模式额外占用约 2376MiB 显存（视觉模块 888MiB + 预留 1488MiB；不需要图片理解时
> 改用普通模式启动可显著提速）；实测该模型在普通模式下可完整驻留显存，
> 开视觉会把约 1537MiB 权重挤回 CPU

**结论：16GB 显存上，27B 模型的"完整驻留"和"视觉能力"只能二选一。**
需要图片理解时，改用更小的模型（如 `gemma-4-12b`，mmproj 仅 167MiB）更合适。

## 9. 速度与保真度：三档取舍

### 9.1 先验证"推测解码是否无损"

推测解码理论上是分布保持的（草稿由主模型验证后接受或拒绝），但**"理论上"不等于
"这个实现里"**。用贪心解码（temperature=0、top_k=1、固定种子）逐字节比对输出：

先做对照，确认基线本身可复现：

| 对照 | 结果 |
|---|---|
| 同配置跑两次 | **3/3 条完全一致** —— 基线可逐字节复现 |
| 只改 `-ub`（256 vs 512，不开推测解码） | **3/3 条完全一致** —— 批形状不影响输出 |
| MTP 跑两次 | **3/3 条完全一致** —— 实现是确定性的 |

对照排除了浮点噪声，再逐组件比对：

| 组件 | 与基线贪心输出比对 | 结论 |
|---|---|---|
| `ngram-map-k` | **3/3 完全一致** | ✅ 无损 |
| `draft-mtp` | **0/3 一致** | ❌ 会改变输出 |

**结论：`draft-mtp` 带来的 1.4–2.1 倍提速，是拿输出保真度换的；`ngram-map-k` 无损。**

这不等于"更差"——只是不再与参考解码一致。但既然无法证明不更差，
就不应该默认打开。

### 9.2 三档定义

| 档位 | KV | 推测解码 | 代码场景实测 | 输出保真 |
|---|---|---|---:|---|
| `quality` 质量 | f16 | 无 | 26.4 t/s | 与参考解码逐字节一致 |
| `balanced` 平衡（默认） | q8_0 | 无 | 26.3 t/s | 与参考解码逐字节一致 |
| `speed` 极速 | q8_0 | draft-mtp + ngram | 34–56 t/s | **会与参考解码不同** |

要点：

- **质量档与平衡档速度几乎相同**（26.4 vs 26.3）。权重完整驻留后，
  KV 精度不再影响吐字速度，只影响显存占用。平衡档省下的显存可用于更长上下文。
- **极速档的提速波动很大（34–56 t/s）**，取决于草稿命中率：
  代码等高度可预测的内容命中率高，散文低。
- `auto` / `maximum` 等旧档位名对齐到 `balanced`，**不会因为改名而悄悄改变输出**。
  启用 MTP 必须显式选 `speed`，且启动时会明确警告保真度代价。

### 9.3 视觉模式：mmproj 放哪

`--no-mmproj-offload` 可以把视觉编码器留在 CPU，把显存全部让给权重。
但图片编码也就随之落到 CPU 上。实测（896×896 图片，缓存未命中）：

| 配置 | 文本生成 | 单张新图端到端 |
|---|---:|---:|
| mmproj GPU / 预留 1488（v1.3.1 前的默认） | 10.5 t/s | 9.9 s |
| **mmproj GPU / 预留 768（新默认）** | **17.8 t/s** | **7.5 s** |
| mmproj CPU / 预留 64 | 26.2 t/s | 29.0 s |

两个发现：

1. **原来的 1488MiB 预留是过头的**，两个维度上都吃亏。预留过多把权重挤到 CPU，
   反过来连视觉编码本身也拖慢了。收到 768 后文本快 69%、图片还快 24%。
2. **mmproj 放 CPU 是真实的二选一**：文本快 47%，但每张新图多花约 21 秒
   （806 个图片 token 在 CPU 上要跑 26 秒）。以文本为主、偶尔看图的用法值得，
   图片密集的用法不值得。

由 `performance.mmproj_offload` 控制（默认 `true` = 留在 GPU）。

### 9.4 完整历程

| 阶段 | 代码场景吐字速度 |
|---|---:|
| 起点：Q4_K_M + ctx 65536 | 6.39 t/s |
| 调参：ctx 16384 + q4_0 KV | 16.34 t/s |
| 换档：UD-IQ4_XS | 26.3 t/s |
| 极速档（牺牲保真度） | 34–56 t/s |

**保持输出保真的前提下 4.1 倍；接受保真度变化则可达 5.3–8.8 倍。**
